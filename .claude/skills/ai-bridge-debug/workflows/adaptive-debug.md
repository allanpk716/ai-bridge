## 第一步：分析问题描述

当用户选择"其他"或提供复杂描述时，需要智能分析症状。

**问题分类：**
- **错误类型**：panic、错误返回、挂起、崩溃、行为异常
- **位置线索**：提到的组件（数据库、API、WebSocket、日志）
- **影响范围**：单个功能、整个系统、特定用户、特定时间
- **频率**：一次性、间歇性、持续发生

## 第二步：快速诊断

根据关键词自动检测问题类型：

| 关键词 | 问题类型 | 工作流 |
|--------|---------|--------|
| panic, fatal, crash | 后端崩溃 | backend-debug.md |
| 日志显示, log says | 日志分析 | backend-debug.md |
| 浏览器, 页面, UI | 前端问题 | frontend-debug.md |
| 连接不上, 无法访问, 拒绝 | 连接问题 | integration-debug.md |
| 慢, 超时, 卡住 | 性能问题 | performance-debug.md |
| API 返回, 404, 500 | API 问题 | api-debug.md |
| WebSocket, SSE, 实时 | 实时通信 | integration-debug.md |

## 第三步：智能代理选择

基于症状分析，选择代理策略：

### 单代理策略（简单问题）
- 后端错误 → 后端分析器
- 前端 UI 问题 → 前端测试器

### 双代理策略（集成问题）
- 前后端通信 → 前端测试器 + 后端分析器（并行）
- API 层问题 → 后端分析器 + API 验证器（并行）

### 全代理策略（复杂问题）
- 性能问题 → 所有代理（并行）
- 完全未知 → 所有代理（并行）

## 第四步：执行和关联

**如果使用多个代理：**
1. 在单条消息中启动所有代理
2. 等待所有代理完成
3. 关联来自不同来源的发现
4. 识别跨域问题的根本原因

**如果使用单个代理：**
1. 启动选定的代理
2. 让代理全面调查
3. 如果发现额外的复杂症状，动态添加更多代理

## 第五步：动态调整

在调试过程中，如果发现：

**初始分类错误：**
- 例：开始认为是前端问题，但发现是后端 API 错误
- 动作：切换到正确的工作流

**问题比预期复杂：**
- 例：简单的 API 错误实际上是数据库锁 + 性能问题
- 动作：扩展代理团队，添加相关代理

**需要更多上下文：**
- 例：日志中的错误不足以诊断
- 动作：读取源代码、配置文件、数据库状态

## 第六步：提供诊断

无论使用多少代理，始终提供：

```markdown
## 问题分析
[描述你发现的问题]

## 根本原因
[根本原因及 file:line 引用]

## 影响范围
[哪些组件受影响]

## 修复方案

### 立即修复
[快速修复以恢复服务]

### 长期修复
[永久解决方案]

## 验证
[如何验证修复有效]
```
</process>
